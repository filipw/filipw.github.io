☁️ Cloud LLMs

  • ✅ Reasoning, complex tasks
  • ✅ Broad world knowledge
  • ✅ Long context windows
  • ❌ Expensive at scale
  • ❌ Latency, round-trips
  • ❌ Privacy concerns

💻 On-Device SLMs

  • ✅ Fast & cheap
  • ✅ Private, offline
  • ✅ Low latency
  • ❌ Limited reasoning
  • ❌ Smaller context
  • ❌ Error-prone on hard tasks
No matter what you choose, you lose - right?

The real cost of cloud inference

  • 📊 1 million queries/day to GPT-5.4
    → ~$10,000 per day
  • 📊 Not all queries are equal
    → "What is the capital of France?" vs. multi-step reasoning
  • ⚠️ Sending trivial queries to frontier models
    → quickly becomes economically irrational

Just use SLMs everywhere?

  • 💲 Cheaper?
    → Yes.
  • 🔒 More private?
    → Yes.
  • 🚫 Reliable enough for production agentic systems?
    → No.
  • 📉 A 1% per-step error rate causes failure after 100 steps
    → compound errors in long agentic pipelines are catastrophic

¹ Meyerson et al., "Solving a Million-Step LLM Task with Zero Errors", arXiv:2511.09030 (2025)

This sets up the need for a smarter hybrid approach. We can't just replace everything with SLMs.

  • 📖 The conventional wisdom "bigger = better" has been decisively challenged
    → Sharma & Mehta, arXiv:2510.03847 (2025)
  • 🤖 Specialized SLMs now match or exceed LLMs at specific agentic tasks
    → function calling, structured output, tool use
  • ⚙️ The bottleneck in agentic systems is orchestration and I/O
    → not raw intelligence

SLM-Default, LLM-Fallback

Route cheap, escalate smart

Sharma & Mehta, arXiv:2510.03847

The cascade concept

  • 🥇 All queries go to the local SLM first (Tier 1)
  • 🔍 A verifier evaluates the SLM response quality
  • ☁️ Only failing queries escalate to the cloud LLM (Tier 2)
  • ❓ The key question: how do we know when the SLM is wrong?

The confidence gate

  • 📊 Self-reported confidence scoring
    → SLM appends CONFIDENCE: N (1–10) to its response
  • 🔬 Other gate options:
    → semantic similarity check
    → output validation against schema
    → tool call success rate

  • ✅ Best pattern to start with - simple to implement

Predictive Router (RouteLLM)

Decide before you generate

Ong et al., RouteLLM, arXiv:2406.18665, ICLR 2025

Two different approaches

Pattern 1 - Reactive Pattern 2 - Proactive
Strategy Generate, then evaluate Predict, then route
When routing? After SLM responds Before any generation
SLM always runs? Yes (even for hard queries) No - skipped if predicted hard
Training required? No - works zero-shot Yes - router trained on preference data
Both are complementary - not competing.

RouteLLM: Learning the routing

  • 🎓 Train a lightweight router to predict query difficulty
    → UC Berkeley + Anyscale, ICLR 2025
  • 📊 Trained on human preference data (Chatbot Arena)
    → learns which queries need a strong model
  • ⚡ Router cost: $3–$40 per million requests
    → vs. $2,000–$15,000 per million LLM generation requests

¹ Ong et al., "RouteLLM: Learning to Route LLMs with Preference Data", arXiv:2406.18665, ICLR 2025

Four router architectures

  • 1️⃣ Similarity-Weighted Ranking
    → retrieves similar queries from training data, uses outcomes to vote → fast, CPU-only
  • 2️⃣ Matrix Factorization 🏆
    → learns latent features per query category → 50% fewer GPT-4 calls to hit 80% performance (CPT80%)
  • 3️⃣ BERT Classifier
    → fine-tuned on preference data → strong balance of speed and accuracy
  • 4️⃣ Causal LLM Classifier
    → Llama-3-8B → most powerful but highest overhead
You don't need a big model to make a smart routing decision

RouteLLM in practice

  • 📦 You need: a preference dataset
    → or use the open-source RouteLLM checkpoints
  • 🔧 Wire the router ahead of your agent graph
    → add a routing node before the SLM/LLM fork
  • 🔀 Tune the threshold: balance cost vs. quality
  • 🛡️ Combine with Pattern 1 as a safety net
    → router for pre-inference, confidence gate for post-inference

Minions

Divide the document. Conquer locally. Synthesize in the cloud.

Narayan et al., arXiv:2502.15964

The long-context problem

  • 📄 Real-world tasks involve large documents
    → 10-K filings, medical records, code repositories
  • ☁️ Sending full documents to cloud LLMs is extremely expensive
    → long context windows multiply token costs
  • 💻 SLMs can't reliably process entire documents
    → limited context window, hallucination on long inputs
  • ⚠️ Naive: let local model read everything, hand off to cloud
    → 30.4× cost reduction but loses 13% accuracy

¹ Narayan et al., "Minions: Cost-efficient Collaboration Between On-device and Cloud Language Models", arXiv:2502.15964 (2025)

Decompose, Execute, Aggregate

  • 🧩 Decompose
    → Remote cloud LLM writes subtask instructions that split the task into single-step chunks
  • ⚡ Execute locally
    → Multiple SLM agents run on individual chunks in parallel
  • 🔗 Aggregate
    → Cloud LLM synthesizes the filtered results into a final answer
  • 🔑 Key insight: The remote model never reads the full document
5.7× cost reduction · 97.9% performance preservation vs. cloud-only

Why this works

  • ✂️ Bite-sized single-step instructions → SLMs never face the long-context problem
  • 🔄 Parallelism is free: each chunk is independent
  • 🎯 The SLM handles what it does best: simple extraction and classification on short text
"MinionsS with an 8B local LM can recover 97.9% of remote-only performance at 18.0% of the cloud cost"

Chain of Agents

Sequential reasoning across document segments

Zhang et al., arXiv:2406.02818

The chain concept

  • 🔗 Multiple worker agents process sequential chunks of a long document
    → each worker reads its chunk + carries forward a running summary
  • 📬 Workers pass their accumulated context to the next worker
  • 🏁 A final manager agent synthesizes all worker outputs into the answer
  • 🔄 Interleaved read-process approach - not input reduction

¹ Zhang et al., "Chain of Agents: LLMs Collaborating on Long-Context Tasks", arXiv:2406.02818 (2024)

CoA vs. other approaches

Approach Problem CoA Advantage
RAG Retrieval has no guarantee of finding relevant info Sequential scan = full coverage
Full-Context Token cost scales with document size Each worker sees only its chunk
Truncation Drops potentially critical content Nothing is discarded
Up to 10% improvement over RAG and Full-Context baselines on QA, summarization, code completion

Hybrid twist: SLM workers, LLM manager

  • 📖 In the original paper, all agents are the same model
  • 🔀 Hybrid variant: SLM workers, LLM manager
  • ⚙️ Workers do what SLMs do best: extract, summarize short chunks
  • 🧠 Manager does what LLMs do best: synthesize, reason, compose final answer

MAKER

A million steps. Zero errors.

Meyerson et al., arXiv:2511.09030

The million-step problem

  • 🚀 LLMs have achieved breakthroughs in reasoning and tool use
  • 📉 But error rates compound in long agentic pipelines
    → 1% per-step error → probability of success after 100 steps: ~37%
  • 📉 After 1,000 steps: ~0.004%
    → essentially guaranteed to fail
  • ❓ Can we solve tasks with over one million steps with zero errors?

¹ Meyerson et al., "Solving a Million-Step LLM Task with Zero Errors", arXiv:2511.09030 (2025)

Extreme decomposition + error correction

Maximal agentic decomposition · first-to-ahead-by-K Error correction · Red-flagging

  • ✂️ Decompose - Break tasks into the smallest possible atomic subtasks (micro-roles)
  • 🗳️ Vote - Multiple SLM instances attempt each micro-task in parallel, output is voted on
  • 🚩 Error correction - Failed steps trigger a red-flag and re-execution with a stronger model
  • 🏆 Result: Towers of Hanoi solved with 1,000,000+ steps and zero errors

The multi-agent advantage

  • 📐 Fundamentally different scaling: horizontal decomposition - not bigger models
  • 🤝 Reliability emerges from consensus, not from individual model intelligence
  • 🔀 Hybrid version: SLMs for micro-tasks, LLM for orchestration and voting arbitration
"Instead of relying on continual improvement of current LLMs, massively decomposed agentic processes may provide a way to efficiently solve problems at the level of organizations and societies."

Putting It Together

Pattern comparison

Pattern Best for SLM role LLM role
SLM-Default Fallback General queries, cost reduction Default responder Fallback for hard queries
RouteLLM High-volume, predictable traffic Simple queries only Complex queries only
Minions Large document Q&A Chunk executor Job writer + aggregator
Chain of Agents Sequential document tasks Sequential workers Final synthesizer
MAKER High-reliability long tasks Micro-task executors Orchestrator + arbitrator

Which pattern to start with?

  • 🚀 Start here: SLM-Default, LLM-Fallback
    → drop-in improvement, zero training required
  • 📊 For high-volume workloads: Add RouteLLM router
    → pre-inference routing for predictable, large-scale traffic
  • 📄 For document-heavy tasks: Minions or Chain of Agents
    → choose by task: parallel extraction vs. sequential reasoning
  • 🔒 For reliability at scale: MAKER decomposition principles
    → when correctness is non-negotiable
